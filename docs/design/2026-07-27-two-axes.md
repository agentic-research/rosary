# Two axes: the store, and how we reach it

**Status:** working draft, uncommitted. Supersedes `2026-07-27-reconciliation-plan.md`
(deleted — its central claim was falsified under adversarial review; see §6).
**Companion:** `2026-07-27-bead-aggregation-findings.md` (raw measurements).

---

## 0. The short version

A day of systematic looking surfaced ~15 defects. **They are four root causes,
and two are already fixed.** The organising principle — the operator's, not
mine — is that rosary has two independent problems that had been discussed as
one:

- **the STORE** — what is true, and where it lives
- **the INTERACTION SURFACE** — how anything reaches it (CLI ↔ API ↔ MCP)

Most of the day's confusion came from proposing store-axis mechanisms for
interaction-axis symptoms. They do not reach. A perfect field-set does not make
`move` callable by an agent.

| # | Root cause | Axis | Instances | State |
|---|---|---|---|---|
| A | **Ambiguity resolved by a silent default** | store | 7 known | **2 fixed** |
| B | **Built, never wired** | cross-cutting | 5 known | inert, non-destructive |
| C | **Surface divergence** — same op, two implementations | interaction | 5 known | P0'd, threaded |
| D | **One-directional boundary** — no promote verb | store | 1 | **fixed (one-shot)** |

Nothing here was created today. It was *found* today.

## 1. Root cause A — ambiguity resolved by a silent default

**The invariant that would kill the class:** *a read path may not mutate, and
ambiguity must fail closed.* Both of today's fixes are instances; the rest are
the same shape.

| Site | Silent default | State |
|---|---|---|
| `connect_bead_store` | both stores present → picks Dolt, drains + renames the other, dropping `notes`/`external_ref`/timestamps and all comments + deps | **FIXED** `rosary-9103f7` |
| `graph` CLI | `if let Ok(store)` swallowed the error — including the fail-closed one added the same hour | **FIXED** `rosary-8a58bc` |
| `find_thread_for_bead` | `LIMIT 1`, no `ORDER BY` → oldest membership wins; 48 beads dual-homed | `rosary-cac78e` |
| `resolve_beads_dir` | `.parent().unwrap_or()` → returns a *relative* path in a main worktree; worktree branch unreachable when `.beads/` is tracked | `rosary-f26fcd` |
| `bead_from_row` | `unwrap_or_default()` → a column a query forgot reads as `""` | ADR-0021 slice 1 |
| `post-push` hook | `[ -d .beads/dolt/$REPO ]` false for every SQLite store → silent no-op; `basename $PWD` on line 1 | `rosary-4ebf52` / `rosary-25e28d` |
| `jsonl_sync` | early `return Ok(false)` for any Dolt repo → cloister's 19/7/1 drift | `rosary-42a5cb` area |

**Why this is the most dangerous category:** its failures are indistinguishable
from success. Every one of these returns "OK".

**Note on scope:** cloister's drift is *this* — a guard clause, fixable in an
afternoon. It is **not** evidence for needing ADR-0020 P2. The earlier plan
claimed it was; that was wrong.

## 2. Root cause B — built, never wired

Capability exists, is correctly typed, and nothing calls it. **Entirely inert —
no instance destroys data.** It costs us *blindness*, not corruption.

| Thing | Population |
|---|---|
| `derived_from` (ProvenanceRef, 5 variants) | **0 / 1125 beads** |
| `SqliteObservationLog` (551 lines, the persistent G-set) | **0 external references** |
| `FieldName::Status` — the only cross-source-joined field | **0 production emitters** |
| `FailureClass::classify` — the dispatch diagnosis | referenced **only in a doc comment** |
| `dispatches.session_id` / `session_ref_id` | **0 / 90 rows** |
| jj workspace creation via `jj-lib` (`rosary-efd300`, shipped) | unreachable — `detect_vcs` returns `Git` whenever `.git` exists, i.e. always in colocated repos |

**The discipline this implies:** an optional field on a create path stays empty
forever. Five independent confirmations. Any new field — context ref, capsule
ref, provenance — must be **required on a single writer**, or it joins this
table.

**Why we are blind about dispatch specifically:** 90 dispatches (6 success, 9
failure, 71 deadletter, all `claude`, all 2026-07-03/04) recorded **no cause**,
because the classifier that would record one is never called. We cannot say why
dispatch fails. That is a wiring gap, not a mystery.

## 3. Root cause C — surface divergence (the interaction axis)

**API is the middle layer between CLI (human) and MCP (agent).** Today it does
not exist, so every operation is implemented once per surface and drifts.

| Verb | CLI | MCP |
|---|---|---|
| `create`, `close` | ✅ | ✅ — the only two sharing `bead_ops`, and the only two that have never drifted |
| `move` | ✅ | ❌ |
| `link`, `update` | ❌ | ✅ |
| `reopen` | ✅ but refuses `done` | ❌ (`update` has no `status` field) |
| `search` | returns 5 | returns 0 for the same intent |

**Consequence:** a bead wrongly marked `done` is **unrecoverable through any
documented surface.** There are 5 such beads, and one of them
(`rsry-118421`, "Unified interface layer: CLI and MCP as projections of the
same core") is the bead asserting this problem is solved.

**It bit three separate sessions on 2026-07-27:** mache (`thread_assign`
reported success, the query disagreed), LLO (couldn't write dep edges — `link`
is MCP-only — so a sequencing plan went in as prose), and this one (`move`
unreachable for the 15 stranded cloister beads).

**Two layers required, not one.** An IR unifies *shape*; it does not unify
*behaviour*. `rosary-e9667c` was a schema-identical call where MCP skipped the
close gate CLI enforced — a generated `inputSchema` would not have caught it.

1. **IR / registry** — one declaration → MCP schema + clap + docs
   (`rosary-d954d6` **P0**, `rosary-08a278`, `rosary-3a5f22`)
2. **Shared execution core** — one implementation the surfaces *call*
   (`rosary-cb1af4` **P0** — already names REST as a consumer)

`bead_ops` is the existence proof for layer 2. The pattern works; it was applied
to two verbs and stopped.

Decade: **`surface-parity`** (`shared-core` / `registry-ir` / `gaps`).

## 4. Root cause D — the one-directional boundary

**Dual state already exists in rosary, accidentally, unnamed.**

| | |
|---|---|
| `.beads/beads.db` (gitignored) | the **working set** — local, in-flight |
| `.beads/beads.jsonl` (tracked) | the **published record** — canonical, shared |
| `--published-from` | the projection maintaining the boundary |

The pre-commit hook exports with `--published-from`, which per its own help
*"refresh[es] only ids already present … local-only store records are never
added."* So the boundary is maintained **in one direction only**: it keeps
published beads current and can never publish a new one.

**Measured:** store 1178 / ledger 1129 / **49 store-only**, including the entire
`agent-work-continuity` decade. Fixed one-shot in `541f55b`; the mechanism gap
is `rosary-bc1918` (**P0**).

**Two consequences:**

1. **`rosary-610ad8`'s dual state is not missing — it is unnamed and missing its
   promote verb.** That is a far smaller problem than "design dual state."
2. **The full-vs-published set difference is a free, programmatic "created
   locally, not yet shared" signal** — most of what `rosary-b64523` wanted a new
   field for, derivable today with no schema change.

**Caveat for whoever builds `publish-one`:** `--published-from` is *correct* for
a public projection (`rosary-b75bec`, vigil pre-release) and *exposure* for a
repo's own record. One flag, two jobs, opposite correct behaviours. Do not just
drop it.

## 5. What actually orders the work

Not a grand sequence. Two independent tracks plus a discipline.

**Store track** — stop loss, then make ambiguity impossible:
1. ~~ambiguous-store fail-closed~~ **done** (`rosary-9103f7`)
2. ~~publish the 49~~ **done, one-shot** (`541f55b`) → `rosary-bc1918` for the verb
3. post-push hook repair (`rosary-4ebf52`/`25e28d`) — still losing data on every SQLite repo
4. deterministic export (`rosary-afdc19`) — cause #2 already fixed (id-sorted); 4 `ORDER BY` clauses remain
5. one reader / one writer (ADR-0021 s1–2) — kills the `unwrap_or_default` class

**Interaction track** — parallel, no dependency on the above:
1. shared execution core (`rosary-cb1af4`)
2. the missing verbs (`rosary-ee49bf` reopen, `rosary-cac78e` unassign, `rosary-882154`)
3. IR/registry (`rosary-d954d6`) + parity conformance (`rosary-1a4c0b`)

**Cross-cutting discipline** — any new field is required on one writer, or it
becomes §2's sixth row.

ADR-0021 states in writing that its slices and ADR-0020's identity work are
**order-free** (*"Either can land first"*), so the tracks genuinely parallelise.

## 6. What the previous draft got wrong

Recorded because the failure is instructive, and because the deleted plan may be
cited from elsewhere.

1. **The "three mechanisms" reduction was false.** It claimed one canonical
   log + fold would resolve store↔ledger drift, orphan routing, *and* false-done.
   It rested on "per-source retention", a mechanism that **does not exist**
   (`grep -rn retention src/` → zero hits). The lattice models per-**source**
   (provenance: linear/github/git); in-flight-vs-canonical is per-**scope**.
   Orthogonal axes. Worse, `fold.rs` joins cross-source disagreement to
   `⊤ = Conflict`, so encoding a branch as a Source would make a feature branch
   legitimately ahead of trunk fold to *Conflict* — the exact case dual state
   exists to legalise.
2. **Dual state is ADR-0020 P4, not P2** — gated behind P3.
3. **Orphan routing cannot be reached by any log mechanism.** `FieldName` has no
   `Thread`/`Decade` variant; routing lives in a third store
   (`~/.rsry/backend.db`) that P2 never opens.
4. **The close-gate arrow was backwards.** ADR-0010: R4b *depends on* the close
   gate. The plan put it downstream, then enforced it upstream via I5.
5. **The root-store rejection was overstated.** §6.2 rejects a *registry over N
   unchanged stores* (N→N+1). A root store as sole authority is N→1 — the
   removal that sentence asks for. ADR-0012 (**Accepted**) already specifies a
   central `~/.rsry/personal.db`, and `rosary-171a4d` — scheduled by the plan
   itself — is literally titled *"root store"*. The question is open; the plan
   closed it by miscitation.
6. **Numbers:** 71 → **42**; LLO's 26 was historical, not current; orphan rate
   62.6% direct but **~73% effective**; `SharedScope` threads 20 → **33**.

**The general lesson**, which is also root cause A one level up: I asserted a
mechanism without checking it existed, and built a plan on it. The corpus was
grep-able the whole time.

## 7. Still open

- **Colocated `detect_vcs`** (`rosary-e80f2a`) — git wins whenever `.git` exists,
  so the shipped jj-workspace path is unreachable in every repo in daily use.
  Gates the capsule model (`rosary-d16978`).
- **`core.hooksPath = .rsry-hooks`** silently disables `.git/hooks/`, including
  the pre-commit framework's config. Winner-take-all, undocumented. Unfiled.
- **Cloister reconciliation** — 19 store-only / 7 ledger-only / 1 conflict, plus
  15 beads stranded in `~/.beads/beads.db`. Parked: its session is live, and
  `import --jsonl` refuses Dolt.
- **Canonicalisation naming is not ours** — substrate-owned by LLO
  (`ley-line-open-b67a73`). Ship deterministic ordering; take the tag later.
- **CAS ≠ CDC.** rosary does content *addressing* (`rosary-bf6c74`, golden-vector
  proven) and chunks nothing.
